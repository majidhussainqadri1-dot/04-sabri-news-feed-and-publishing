# File 04 V12.3 — P02 Malformed Evidence Regression and Root Cause (2026-11-14)

**Classification:** SOURCE-ONLY operational-tool integrity defect, not a confirmed defect in live WordPress/PHP. **Scope:** `tools/verify_file04_installed_parity_offline.py` and `STATUS.md`. **Production state:** not accessed or modified. **Historical baseline:** `main` `21422390d76cdc21386bebeb6138de0012e283bc`, exact-main run `43599406648` 4/4 passed; the baseline did not contain the new negative test cases.

## 1. Reproduced source defect and impact

The P02 offline tool took a host JSON file supplied by a private operator and compared its reported installed file tree against a release ZIP. Its input parser assumed that the JSON root, nested `file04` evidence, flags and timestamp had conventional types.

**Reproduction (against exact baseline artifact, before changes):**

- Host JSON root `[]` → nonzero exit with uncaught `AttributeError: 'list' object has no attribute 'get'`, raw Python traceback on stderr, **no machine-readable UNVERIFIED receipt**.
- Timestamp property as a JSON integer → uncaught `AttributeError: 'int' object has no attribute 'replace'`, raw traceback on stderr, **no safe audit receipt**.
- Boolean and counter properties could be supplied as strings/booleans of the wrong type and were not validated strictly before classifying files. This was a validation gap, not a demonstrated Live false-match incident.
- The tool did not independently verify that the approved ZIP's embedded `PACKAGE-CHECKSUMS.sha256` manifest actually covered and matched every embedded package file. This allowed a structurally well-formed but internally corrupted purported approval artifact to proceed to field comparisons rather than fail on its own integrity.

The behavior violates the File04 source diagnostic `FAIL-CLOSED` contract; exact host access is still unavailable. No evidence establishes that these inputs were ever supplied to a production system.

## 2. Narrow root cause

Insufficient **structural/type validation** and a missing **independent approved-ZIP manifest** check in the *offline Python source tool*. The PHP adapter, WordPress deployment, DB schema and user content are **not** implicated by this reproduction.

## 3. Minimal fix on a separate source branch

- Validate JSON root and `file04` are plain objects; require collector/schema identity, `ok=true` and no-secret/no-content-export flags with strict types.
- Require strict UTC ISO-8601 timestamp string and fresh observation window, not `datetime.fromisoformat` applied blindly to arbitrary JSON.
- Require literal JSON booleans for scan and manifest acceptance; enforce non-Boolean integer counter type and zero missing/mismatched/extra files; require expected manifest count.
- Validate the approved ZIP's checksum manifest independently against **all** extracted ZIP files (except the manifest itself), with bounded size and safe filename rules.
- Reject directory/symlink ZIP members and duplicate/unsafe paths; keep uncompressed-size bounds.
- On any malformed host report return `UNVERIFIED` with a sanitized JSON reason and a nonzero exit, **without printing traceback, host paths, patient details or exception content**.
- Preserve the approved states `MATCH`, `MISMATCH`, `UNVERIFIED` for **filesystem parity only**. Even MATCH is not a WordPress installed/active-state, actual DB version or QA-24 Live completion receipt.

## 3B. Second reproduced source defect: package checksum / parser race

The baseline verifier opened the ZIP path once for archive iteration and read it **again afterward** to calculate its SHA-256. A deterministic filesystem replacement fixture used two different, internally well-formed ZIPs:

- The verifier iterated the previously opened ZIP's original members, which matched the synthetic host report.
- The filesystem path was swapped for a second ZIP before the verifier read the path again to compute the package SHA.
- **Reproduced baseline result:** `filesystem_parity=MATCH` while `approved_zip_sha256` was the SHA of **the replacement ZIP**, not the bytes inspected for the alleged MATCH.

This is a genuine source integrity defect in the offline evidence verifier, **not evidence of an actual hostile operation at Hostinger**. The corrected code loads the bounded ZIP bytes into one immutable in-memory snapshot, performs both `zipfile.ZipFile(io.BytesIO(snapshot))` parsing and `sha256(snapshot)`, and checks actual byte length after the read. A deterministic race fixture swaps the disk path during the ZIP open and asserts that the report checksum remains bound to the inspected original bytes.
